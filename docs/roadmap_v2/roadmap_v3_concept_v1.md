# Roadmap V3 Concept V1

## Purpose

This note revises the V2 roadmap after a deeper review of:
- the external roadmap draft
- the exported roadmap conversation
- the longer strategy conversation in the full roadmap PDF
- the ERI proposal
- the GreenYield / AllocationLab summary
- the current `semantic-patterns` repo state

The goal is not to optimize for a short burst of interview preparation or a single portfolio artifact. The goal is to define a realistic 3-6 month transition from a successful paper-centered repository into a reusable disclosure-intelligence lab.

## Bottom line

The right framing is:
- one reusable lab core
- one near-term proof surface
- one executable next application
- one architecture-first future application

In that framing:
- the current AI-washing project is not the end-state product
- it is the first completed research program built on the core
- FilingLens is not a new research project; it is the first packaging surface for what already exists
- ERI is the next real application build
- AllocationLab is the later architecture track, not a concurrent implementation target

## Why V2 needs revision

V2 was directionally strong. It correctly shifted away from generic Upwork growth and toward reusable engine clarity. But it still carried too much near-term load across too many fronts:
- engine clarification
- ERI interview preparation
- AllocationLab architecture
- FilingLens proof
- public packaging
- outreach / positioning

That is a strong strategy set, but still too crowded as an execution stack.

The new context changes the center of gravity:
- FilingLens is already conceptually close to done and mainly needs packaging / surface design
- the real long-term opportunity is not a short-term interview kit alone
- the real opportunity is to turn this repo and director discipline into a reusable lab that can support multiple domain programs over time

## Revised strategic claim

The repo should now be treated as a disclosure-intelligence lab in transition.

That means the current thesis chapter becomes:
- proof of extraction discipline
- proof of benchmark / IRR discipline
- proof of evaluation and reporting discipline
- proof of table / figure / memo delivery discipline

The repo should not yet be presented as a fully generalized product platform. But it should be deliberately reorganized in thought and documentation so that the AI-washing paper is understood as phase one of a broader engine.

## The real role of each project

### AI-washing
Role:
- completed proof program
- research-grade validation case
- first evidence that the engine can produce an auditable end-to-end output

What it proves:
- text extraction and scoring can be run reproducibly
- human labeling and IRR can be operationalized
- external validation can be made concrete
- empirical reporting can be turned into paper-support assets

What it does not prove:
- that the current taxonomy is reusable as-is across domains
- that the current models are production-ready in new contexts
- that the repo should be split or productized immediately

### FilingLens
Role:
- packaging surface
- visible public-safe proof
- bridge between academic credibility and portfolio / market credibility

What FilingLens should be:
- a thin proof layer using public documents
- a clean, explainable workflow slice
- a demoable artifact that shows input -> extraction -> scoring -> memo/report output

What FilingLens should not be:
- the core roadmap destination
- a large new research build
- a major UI or product engineering program right now

### ERI
Role:
- next executable domain application
- first genuine reuse test of the lab core in a new problem setting
- strongest institutional / interview / postdoc-adjacent opportunity

Why ERI matters most now:
- closest to the existing workflow pattern
- naturally extends the benchmark / IRR / scoring discipline
- fits supervisor and partner conversations directly
- can create a credible 90-day pilot without pretending to be a finished product

### AllocationLab
Role:
- architecture-first future track
- long-horizon decision-system ambition
- later layer that may consume outputs from disclosure-reliability systems

Why AllocationLab must remain later:
- its unit of analysis is different
- its data model is different
- its scoring logic is much broader
- its optimization / financing / policy layer is genuinely new
- it can sprawl quickly if treated as a build now

## Revised roadmap principle

The next 3-6 months should optimize for controlled transition, not simultaneous expansion.

The practical rule should be:
- stabilize the core
- package one thin proof
- incubate one new application
- preserve one ambitious future architecture
- defer broad public / freelance expansion until the above are coherent

## Recommended lanes

### Lane 0. Hold the paper lane steady

Use the current paper as a credibility asset, not an active construction site, until feedback arrives.

Allowed work:
- feedback response
- appendix / technical clarification if requested
- careful archival and source-of-truth cleanup

Do not do by default:
- a new year-2000 expansion
- new empirical sweeps without feedback
- paper-driven repo churn

### Lane 1. Lab boundary and source-of-truth

Objective:
- define what the reusable lab actually is
- separate reusable workflow layers from AI-specific content
- make the current repo legible as a foundation rather than a one-off project

Key deliverables:
- `engine_boundary_memo_v1.md`
- `source_of_truth_map_v1.md`
- `artifact_policy_v1.md`
- `lab_transition_architecture_v1.md`

Acceptance gate:
- the repo can be explained as a reusable disclosure-intelligence lab in five minutes without hand-waving

### Lane 2. FilingLens packaging surface

Objective:
- turn the current AI-washing workflow into one clean proof artifact that others can understand without reading the whole repo

Key deliverables:
- `filinglens_surface_note_v1.md`
- `filinglens_thin_slice_spec_v1.md`
- one public-safe proof run on a bounded set of filings
- output screenshots or memo samples

Acceptance gate:
- one public-safe example can be shown end to end with minimal explanation

### Lane 3. ERI incubation

Objective:
- prepare and then begin the first real second-domain build

Key deliverables:
- `eri_interview_kit_v1.md`
- `eri_90_day_pilot_v1.md`
- `eri_q_and_a_v1.md`
- `eri_taxonomy_v0_1.md`
- one small transfer-proof artifact on a bounded sustainability corpus

Acceptance gate:
- the work has moved beyond interview prep into a credible early application path

### Lane 4. AllocationLab architecture preservation

Objective:
- keep the larger opportunity alive without turning it into an uncontrolled immediate build

Key deliverables:
- `allocationlab_architecture_v1.md`
- `allocationlab_gap_matrix_v1.md`
- `allocationlab_synthetic_case_v1.md`

Acceptance gate:
- the future vision is concrete enough to discuss seriously, but still bounded as architecture-first

### Lane 5. Packaging and outreach

Objective:
- convert the strongest artifacts from Lanes 1-3 into portfolio, partner, or hiring material

Key deliverables:
- public-safe case study copy
- supervisor / collaborator briefing pack
- portfolio-facing explanation of the lab and its first proof surface
- selective outreach assets only after the above exist

Acceptance gate:
- each artifact has a clear audience, privacy class, and purpose

## 3-6 month execution map

### Phase A. First 2-3 weeks
Focus:
- lab clarification, repo legibility, source-of-truth

Primary outputs:
- engine boundary memo
- source-of-truth map
- transition architecture note
- artifact policy

This phase is mostly documentation and boundary control, not refactoring.

### Phase B. Weeks 3-6
Focus:
- FilingLens proof surface and ERI interview / pilot preparation

Primary outputs:
- FilingLens thin slice spec
- FilingLens proof artifact
- ERI interview kit
- ERI 90-day pilot outline

This phase should still avoid a large new implementation push.

### Phase C. Weeks 6-12
Focus:
- ERI incubation

Primary outputs:
- taxonomy v0.1
- benchmark design
- IRR plan
- bounded transfer-proof run

This is the first place where the lab proves cross-domain reuse in practice.

### Phase D. Months 3-6
Focus:
- mature ERI into a pilot path
- preserve AllocationLab architecture
- package the strongest proof artifacts

Primary outputs:
- ERI pilot memo and gap map
- AllocationLab architecture pack
- public-safe portfolio surface

## What should remain out of scope for now

Not now:
- splitting the repo into multiple repos
- extracting a new standalone engine package
- building full production UIs
- full AllocationLab implementation
- broad Upwork positioning as a roadmap driver
- generic AI-agent branding as the main identity

These can all happen later, but they should follow proof and boundary clarity, not precede them.

## Critical guidance on identity

The strongest identity is not:
- generic AI freelancer
- general agent builder
- broad enterprise AI engineer

The strongest identity is closer to:
- builder of auditable decision-intelligence systems for disclosure, sustainability, and finance
- or builder of explainable AI workflows for text-based measurement, scoring, and decision support

That identity is more coherent with:
- the paper
- FilingLens
- ERI
- AllocationLab
- director

## Repo transition rule

The repo should be evolved by boundary-setting and selective adapters, not by a sweeping rewrite.

The next changes should mostly be:
- clearer maps
- clearer artifact lanes
- clearer naming
- bounded proof surfaces
- explicit separation between core workflow and domain-specific semantics

The next changes should not be:
- wholesale renaming
- extraction for its own sake
- product UI ambition before workflow clarity

## Immediate recommendation

The immediate next move should still be strategy-to-structure, not a new application build.

But after this review, the first packet should be slightly reframed.

Instead of thinking only in terms of `engine boundary memo`, the next packet should be understood as:
- define the lab core
- define the source of truth
- define what FilingLens is
- define what ERI reuses
- define what AllocationLab does not yet attempt

That creates the right base for the next 3-6 months.
