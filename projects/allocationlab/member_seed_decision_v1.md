# AllocationLab Member Seed Decision V1

## Decision

Current status:
- staged placeholder, architecture-first, not a true local workspace member yet

## Why

AllocationLab is important, but it is still the least mature for immediate member seeding.

Current pressures suggest caution:
- architecture and ontology are still primary
- implementation scope is not yet settled
- the project may evolve significantly before a stable local code boundary appears

## Recommendation

Treat AllocationLab as:
- a planned future project member
- initially architecture-first, with private-local and staged materials as needed
- path-dependent or staged external intake if implementation begins elsewhere first

Do not force it into a local buildable member until:
- the scenario and dependency model are clearer
- the package/member scope is stable enough to survive change
- the member would mean more than a placeholder directory

## Trigger for promotion

Promote AllocationLab from staged placeholder to real member seed when:
- architecture notes stabilize into a clear member scope
- there is a local code surface worth owning
- private-local and tracked boundaries are explicit
- the project has enough implementation pressure to justify a real buildable member path

## Bottom line

AllocationLab should remain a planned placeholder for now.
That protects the workspace from pretending architecture-first work is already a stable package member.
